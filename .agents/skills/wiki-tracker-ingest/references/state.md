# Состояние обработки и запуск

Эту инструкцию читай при рабочем запуске. Файлы получателя в `.local/tracker-sync/` только читаются. Состояние смысловой обработки хранится отдельно, в `.local/tracker-wiki/`. Оно нужно для продолжения после обрыва; при переносе вики на другой компьютер сохраняй его вместе с исходниками. Не помещай токены в состояние или журналы.

## Проверка и разрешение

Запускай `scripts/queue.py` доступным Python, передавая команду `status`, `begin` или `finish`. По умолчанию корень вики определяется по расположению скрипта; `--root` нужен для изолированной проверки.

`status` ничего не меняет. Возвращает:

- `enabled` — разрешена ли именно текущая версия скилла;
- `bundleSha256` — контрольную сумму `SKILL.md`, этой инструкции, скриптов и метаданных;
- `processedCursor` и `receivedCursor` — границы обработки и получения;
- `batches` — следующие полные порции, их пути и контрольные суммы;
- `pendingQuestions` — сохранённые нерешённые вопросы;
- `activeRun` — незавершённый проход, если он есть.

После явного принятия Глебом запиши в `approval.json` статус `approved`, текущий `bundleSha256`, дату ISO с часовым поясом и краткое основание из чата. Не принимай эту версию за Глеба. Любое изменение файлов скилла меняет контрольную сумму и требует новой проверки перед автоматическим запуском.

## Проход

`begin --max-batches N` фиксирует не более N следующих порций; по умолчанию одну. Создаёт `.local/tracker-wiki/active-run.json` через исключительное создание файла и отдельную папку `runs/<runId>/`. Второй `begin` отклоняется. Разрешён и проход без новой порции, чтобы обработать ответы на вопросы.

В папке прохода до записи файлов сохрани исходные версии целевых страниц, после подготовки — полные тексты, diff и основания. До вызова MCP сохрани в `operations.json` ID действия, `operationId`, точные параметры и после ответа — результат проверки. При обрыве дополняй тот же журнал.

Если проход незавершён, используй его `runId`, фиксированный список порций и журнал. Скрипт не снимает блокировку по времени: старый проход сначала надо восстановить и закончить. Если исполнитель ещё работает, другой запуск заканчивается без записи. Сломанное состояние не исправляй удалением файлов.

## Итог прохода

Подготовь JSON в папке прохода и передай его в `finish --result <абсолютный путь>`. Формат:

```json
{
  "runId": "ID из begin",
  "outcomes": [
    {
      "path": "относительный путь порции из begin",
      "sha256": "её исходная контрольная сумма",
      "result": "applied",
      "evidencePath": ".local/tracker-wiki/runs/ID/Проверка.md"
    }
  ],
  "files": [
    {"path": "wiki/Трекер/2026-10-26/Неделя.md", "sha256": "контрольная сумма сохранённого файла"}
  ],
  "pendingQuestions": [
    {"id": "постоянный ID", "path": "На проверку/Трекер — вопросы/ID/Вопрос.md", "taskId": "ID карточки или null"}
  ],
  "resolvedQuestions": [],
  "dailyTasks": {},
  "pendingOperations": [],
  "summaryPath": ".local/tracker-wiki/runs/ID/Проверка.md"
}
```

Для каждой зафиксированной порции нужен один итог: `applied`, `no_change`, `waiting` или `mixed`. В `Проверка.md` укажи охват чтения, внесённое, вопросы и ограничения; итог всего файла нельзя ставить после выборочного чтения. Скрипт проверяет целостность, но не подтверждает качество смыслового разбора за агента.

`files` содержит созданные или изменённые файлы и контрольные суммы; удаления перечисли отдельно в `Проверка.md` и проверь ссылки. `pendingQuestions` — полный оставшийся список, включая прежние нерешённые вопросы. Для снятых с очереди вопросов в `resolvedQuestions` укажи `id` и `evidencePath` с сохранённым решением. Закрытые вопросы убирай только после проверки результата и сохранения решения; материалы переноси в историю после `finish`. `dailyTasks` хранит связь московской даты с ID служебной карточки. `pendingOperations` хранит несделанные операции MCP с неизменными параметрами, если локальный ответ уже принят, а сервер недоступен.

`finish` проверяет совпадение порций и сохранённых файлов, существование материалов вопросов и итога, сохраняет квитанцию, атомарно обновляет `state.json` и только затем убирает блокировку. При обрыве после записи состояния повтор того же `finish` завершает проход без повторного внесения вики.

Сам скрипт не редактирует вики, не вызывает MCP, не решает вопросы и не создаёт коммиты. Это делает агент по `SKILL.md`.

## Расписание

Отдельная задача проекта **LLM Wiki** запускается раз в день в 09:00, Europe/Moscow. Её ID — `automation`, тип — `cron`, выполнение — в основной папке проекта `<корень Wiki>`. Она не привязана к чату настройки: каждый запуск берёт инструкции и очередь из файлов проекта. Результаты доступны в разделе расписаний приложения. Ответить на сохранённый вопрос можно в карточке трекера или в любом чате Codex с доступом к этому проекту.

Для изменения расписания сначала перечитай его через `automation_update` и сохрани остальные поля. Не создавай второе расписание вместо изменения существующего. Каждый запуск читает этот скилл и проверяет очередь. Пустая очередь не требует разбора; сама проверка выполняется в сеансе агента. Новые порции и ответы обрабатываются в общей очереди, независимо от места ответа.

Для локальных файлов компьютер должен быть включён, а приложение работать — [официальная документация расписаний](https://learn.chatgpt.com/docs/automations). После пропущенных запусков следующий проход продолжает с сохранённой границы. Не полагайся на автоматическое воспроизведение каждого пропущенного времени. Получение свежих текущих задач по MCP не требует ожидания этого расписания.
