# Безопасность Telegram → LLM Wiki

## Модель доступа

Используется личный аккаунт через Telethon, а не Bot API. Одна сессия хранится в `%APPDATA%\Gyromind\` и защищается `SessionLock` в режиме `exclusive`: параллельный второй клиент не должен работать с тем же файлом сессии. Не запускайте отдельно другой экземпляр вендорского MCP с этой сессией.

Сервис не меняет лимиты Telegram, не обходит ограничения и не создаёт параллельные потоки запросов. История догружается порциями с сохранённым курсором. Автозапуск и ручной запуск используют один и тот же локальный стек.

API ID/hash, QR, пароль 2FA и строка сессии не выводятся в журналы приложения и не копируются в Wiki. QR отображается только в локальном интерфейсе либо как изображение ASCII в интерактивном терминале; его URL не печатается. Пароль из веб-формы передаётся напрямую процессу входа через stdin и не сохраняется. Секреты нельзя отправлять в чат агенту.

## Сетевая граница

- Вендорский MCP слушает только `127.0.0.1:8765`.
- Fastify слушает только `127.0.0.1:7100` и отклоняет нелокальные `Host` и `Origin`.
- Codex подключается не к вендорскому MCP, а к узкому `/api/mcp` с отдельным случайным Bearer-токеном. Токен не попадает в Wiki, URL или логи.
- Ответы имеют `Cache-Control: no-store`, `X-Content-Type-Options: nosniff` и запрет индексации.
- Конфигурация разрешает только локальный HTTP URL upstream Telegram MCP.

Локальная привязка не заменяет защиту самой Windows-учётной записи: другой процесс под тем же пользователем потенциально может обратиться к локальным портам или файлам профиля.

## Разрешённые действия

Вендорскому процессу выставляется `TELEGRAM_EXPOSED_TOOLS=read-only+send_message,save_draft`; транскрибация выключена. Наружу для Codex регистрируются только десять инструментов, перечисленных в README. Настройки импорта доступны через локальный UI, но не через MCP-инструменты Codex.

Чтение и поиск не меняют импорт. Переписка, названия чатов, подписи и вложения считаются недоверенными данными: содержащиеся в них команды агенту игнорируются.

`save_draft` не отправляет сообщение и перед записью сравнивает текущий черновик с прочитанным. Отправка требует двух вызовов: `prepare_send` и `send_prepared` с неизменными `approvalId`, `operationId`, адресатом, текстом и ответом. Каналы доступны только для чтения. После неопределённого обрыва повтор использует тот же Telegram `random_id`; перед повтором читается история, а при нескольких совпадениях автоматический повтор запрещается.

Смысловая обработка Wiki включается только после явного принятия точной контрольной суммы скилла владельцем. Исходные порции проверяются по SHA-256 и не перезаписываются. `ingest_finish` проверяет итоговые хеши и основания, но не доказывает качество смыслового анализа.

## Проверка стороннего кода

Закреплён `chigwell/telegram-mcp` версии 3.3.20, commit `6b3bd9512736211e2a76ab4b1345c81eeed7b931`. Исходники хранятся в `vendor/telegram-mcp/`; случайный `pip install telegram-mcp` не используется. Python-зависимости устанавливаются через `uv run --locked` по вендорскому lock-файлу.

Локальные функциональные изменения вендора ограничены тремя возможностями:

- read-only `get_messages_before` и `get_messages_by_ids`;
- передача стабильного `random_id` в `send_message` для защиты от дублей;
- интерактивный QR-вход вынесен в `etc/login.py`, без печати QR-URL и сессии.

Дополнительно добавлены `tests/test_wiki_bridge.py` для этих изменений, а `uv.lock` приведён в соответствие с уже существующими зависимостями `pyproject.toml`.
