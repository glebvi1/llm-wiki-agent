# Состояние обработки Telegram

Работай через MCP `telegram`, а не прямыми правками `.local/telegram-wiki/state.json`. Состояние и журналы нужны для продолжения после обрыва. API ID/hash, строка сессии и Bearer-токен находятся в `%APPDATA%/Gyromind/`, не в Wiki, Git или журналах.

## Проверка и разрешение

`ingest_status` ничего не меняет и возвращает:

- `enabled` — принята ли текущая контрольная сумма скилла;
- `bundleSha256` — SHA-256 всех файлов скилла, кроме `approval.json`;
- `batches` — новые порции с относительными путями, хешами и числом событий;
- `activeRun` — незавершённый проход;
- `pendingQuestions` — полный сохранённый список вопросов;
- `processedCount` — число завершённых порций.

После явного принятия Глебом запиши в `approval.json`:

```json
{
  "status": "approved",
  "approvedBundleSha256": "значение из ingest_status",
  "approvedAt": "ISO-дата с часовым поясом",
  "evidence": "краткое основание из чата"
}
```

Не принимай скилл за Глеба и не считай настройку интеграции таким принятием.

## Проход

`ingest_begin` принимает необязательный `maxBatches` от 1 до 20, по умолчанию 1. Он фиксирует `runId`, пути и SHA-256 порций. Повтор при существующем проходе возвращает тот же `activeRun` с `recovered: true`. Не создавай второй проход и не снимай блокировку вручную.

До операций сохрани в `.local/telegram-wiki/runs/<runId>/operations.json` `operationId`, точные параметры и результат. В `Проверка.md` фиксируй охват, основания, diff и проверки. Новые порции, появившиеся после `begin`, относятся к следующему проходу.

## Итог

Передай в `ingest_finish` объект в поле `result`:

```json
{
  "runId": "ID из begin",
  "outcomes": [
    {
      "path": "Исходники/Telegram/Чат — chat-123/2026-11-11/ID.json",
      "sha256": "SHA-256 исходной порции",
      "result": "applied",
      "evidencePath": ".local/telegram-wiki/runs/ID/Проверка.md"
    }
  ],
  "files": [
    {
      "path": "wiki/Проекты/Проект/Проект.md",
      "sha256": "SHA-256 сохранённого файла"
    }
  ],
  "pendingQuestions": [
    {
      "id": "telegram-123-45-project",
      "path": "На проверку/Telegram — вопросы/ID/Вопрос.md",
      "taskId": "ID или null"
    }
  ],
  "resolvedQuestions": [
    {
      "id": "прежний-ID",
      "evidencePath": "Исходники/Telegram/Уточнения/2026-11-11/ID.md"
    }
  ],
  "summaryPath": ".local/telegram-wiki/runs/ID/Проверка.md"
}
```

`outcomes` должен точно соответствовать порциям `begin`. Допустимы `applied`, `no_change`, `waiting`, `mixed`. `files` содержит все созданные или изменённые файлы с их фактическими SHA-256. Пути относительные, внутри Wiki. `pendingQuestions` — полный оставшийся список, включая прежние. Для снятых вопросов нужен `resolvedQuestions` с сохранённым решением.

Сервер проверяет неизменность исходников, хеши файлов и существование оснований. Это техническая проверка, а не подтверждение качества смыслового разбора. Повтор того же `finish` возвращает `recovered: true` без повторного внесения; другой итог с тем же `runId` отклоняется.

## Расписание и ручной запуск

Отдельная Codex-задача `telegram-wiki` запускается ежедневно в 09:00 по Москве, как и обновление из трекера. Кнопка «Обновить сейчас» сначала получает выбранные чаты, затем запускает тот же скилл через `codex exec`. Не создавай второе расписание.

Локальный Telegram MCP и сервис должны работать на включённом компьютере. После пропуска продолжай с сохранённых порций; не выдумывай автоматическое выполнение каждого пропущенного времени. Свежие чтение, черновики и отправка доступны через MCP отдельно от расписания и не меняют настройки импорта.
